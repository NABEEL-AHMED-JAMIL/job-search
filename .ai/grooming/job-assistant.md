# Grooming -- Job Assistant

Feature `job-assistant`, row 5 of [../discovery/features.md](../discovery/features.md). Status
**new**: the old app has no counterpart, so this document is about whether what shipped is
*complete and correct*, not about parity.

All paths are relative to `/Users/nabeel.amd93/Desktop/Old-School`.

---

## 1. Purpose

Someone looking at a job in the console has a small set of recurring questions, and today each one
means leaving the screen they are on:

> *When does this thing run next? Where does it put its files? Why does it keep failing? How often
> does it actually succeed? Give me its runs in a spreadsheet.*

The job assistant answers those in place. It sits beside one job -- as a page at
`/jobs/:jobId/assistant` and as a floating panel over the jobs list and that job's run history --
and it answers **only about that job**. Ask it about another job, about other tenants, or about
users, and it says no and names the job it does know about.

The scope rule is the product, not a caveat. The component's own header says so
(`scheduler1/next/src/app/features/jobs/assistant/job-assistant.ts:27-34`): answers are *composed*
from the job's record and runs rather than generated by a model, "the brief was that it must not
wander into other jobs, and a scope rule enforced in code cannot be talked out of it the way a
prompt can. It also means every number on screen is the real one, and the thing works without any
AI provider configured."

There is a second, unused implementation of the same idea on the server that *does* call a model.
Section 2.3 covers it.

## 2. Existing behaviour

The old app has nothing here. `askAssistant` returns zero matches across the whole of
`scheduler1/src` (verified), and there is no assistant, chat or Q&A screen in
`scheduler1/src/app/app.routing.ts`. Everything below is the new app plus the backend.

### 2.1 The shipped client -- rule-based, no model call

Four files, 1,366 lines including tests, at
`scheduler1/next/src/app/features/jobs/assistant/`:

| File | Lines | What it is |
|---|---|---|
| `job-assistant.ts` | 261 | The component: load, ask, export |
| `job-assistant.html` | 213 | Composer, presets, transcript, five block renderers |
| `job-assistant.intents.ts` | 89 | Question -> intent, plus the scope refusal |
| `job-assistant.answers.ts` | 320 | Intent + facts + runs -> answer blocks, and the CSV writer |

**Three places it appears.** One component, three mounts:

| Where | Evidence | Mode |
|---|---|---|
| Page `/jobs/:jobId/assistant` | `scheduler1/next/src/app/app.routes.ts:78-82`, lazy, no `minRole` | full |
| Panel over the jobs list | `features/jobs/jobs.html:420-452`, opened from the row menu at `jobs.html:239` via `openAssistant()` (`jobs.ts:137-140`) | `compact=true` |
| Panel over one job's run history | `features/jobs/history/job-history.html:383-412`, opened by the "Ask about this job" button at `job-history.html:52-60` | `compact=true` |

`compact` (`job-assistant.ts:49-54`) is the same component without page chrome. Both panels are
`fixed bottom-4 right-4 z-50 w-[34rem] max-w-[calc(100vw-2rem)]`, height
`min(40rem, calc(100vh - 3rem))`, with minimise, close, and a "Full page" link to the route
(`jobs.html:421-440`, `job-history.html:384-405`). The host gets `.assistant-fills-panel`
(`job-assistant.ts:45`, CSS at `scheduler1/next/src/styles.css:639-644`) so the transcript scrolls
inside the panel instead of the host sizing to its content.

The route is **not in the shell navigation** -- `assistant` returns no match in
`features/shell/shell.ts` -- and is not mentioned in `features/docs/docs.ts`. It is reachable only
from a job row, from run history, or by typing the URL.

**What it loads.** On construction and on every `jobId` change, an `effect`
(`job-assistant.ts:142-150`) clears the transcript, the question and the runs, then fires two GETs
(`job-assistant.ts:153-183`):

| Call | Feeds | On failure |
|---|---|---|
| `sourceJob.json/fetchSourceJobDetailWithSourceJobId?jobId=` | `detail()` -> `facts()` | sets `error()`, screen shows a retry card |
| `sourceJob.json/fetchSourceJobQueueListWithJobId?jobId=` | `runs()` | **swallowed silently** (`job-assistant.ts:181`) |

A monotonic `loadTicket` (`job-assistant.ts:158,163,177`) drops a late response from a job the user
has already navigated away from.

`facts()` (`job-assistant.ts:88-110`) flattens the detail DTO into the 17-field `JobFacts`
(`job-assistant.answers.ts:12-37`): id, name, status, execution, priority, `lastJobRun`,
`assignedUsername`, task name/type/topic/pipeline, bucket, input and output folder, home page, and
the whole scheduler sub-object. The Kafka topic comes through `parseTopicPartition`
(`job-assistant.ts:102`).

**Intents.** `classify(question, jobId)` (`job-assistant.intents.ts:52-72`) runs three checks in
order:

1. `OTHER_JOB_ID = /(?:job\s*#?|#)(\d{3,})\b/i` (`:25`). A different id -> `out-of-scope`, and the
   id is carried on `mentionedJobId` so the refusal can name it.
2. `FLEET_WORDS` (`:26`) -- `all|other|every|another|each` + `jobs|tasks|tenants|users` -- and
   `OTHER_SUBJECT` (`:28`) -- `users|tenants|organisations|organizations|accounts` -> `out-of-scope`.
3. Seven ordered regexes (`:30-39`) -> `stats`, `failures`, `schedule`, `target`, `history`, `task`,
   `summary`. No match -> `unknown`.

Nine `Intent` values in all (`:8-17`), of which seven produce answers, one refuses and one is the
fallback guide. Six get preset buttons (`PRESETS`, `:82-89`); `task` is reachable only by typing.

**Answers.** `answerFor(intent, facts, runs, mentionedJobId)`
(`job-assistant.answers.ts:142-273`) returns a list of blocks -- `text`, `facts`, `stats`, `chart`,
`runs` (`:50-55`) -- which `job-assistant.html:119-207` renders through a `@switch`:

| Block | Rendered as | Template |
|---|---|---|
| `text` | A paragraph; tinted `--color-warn-600` with an alert glyph when `refused` | `:122-128` |
| `facts` | Two-column `<dl>` on `sm` and up | `:130-139` |
| `stats` | Four tiles -- Runs, Success rate, Average, Longest | `:141-158` |
| `chart` | Outcome donut + "Slowest runs" ranked bar | `:160-174` |
| `runs` | Table: run id, started, status pill, message, link to that run's logs | `:176-206` |

`computeStats` (`:69-100`) is careful in ways worth keeping: success rate is measured against runs
that reached a verdict (`Completed + Failed`) rather than every run (`:85,:94`), a duration is
counted only when both ends exist and the result is non-negative (`:76-82`), and a job with no runs
reports `null` rather than zero (`:94-96`). `humanMoment` (`:108-115`) turns the API's naive
`2026-08-19T00:01:27.90799` into `19 Aug 2026, 00:01` and returns anything unparseable untouched
rather than "Invalid Date".

Turns are prepended, newest first, keyed on a monotonic `turnId` (`job-assistant.ts:19-25,192`).
"Clear" empties the list (`:203`). Nothing is persisted -- a reload loses the conversation.

**Dictation.** `DictationService` (`shared/ui/dictation.service.ts`), shared with the file chat.
The microphone is claimed under `assistant-${jobId}` (`job-assistant.ts:63`) so two open assistants
cannot both listen, speech is appended to what is typed rather than replacing it (`:67-72`), and the
button is hidden entirely where the Web Speech API is absent (`:61`, `dictation.service.ts:23-25`).

**Export.** `exportRuns('csv' | 'xlsx')` (`job-assistant.ts:211-249`). `runsToCsv`
(`job-assistant.answers.ts:291-319`) writes eight columns -- Run, Job, Status, Queued, Started,
Ended, Duration (s), Message. CSV is saved directly; XLSX posts the same CSV to
`fileChat.json/exportFile` with `sourceFormat: 'csv', targetFormat: 'xlsx'` and saves the base64
that comes back (`:229-243`), so there is no spreadsheet library in the browser. With no runs, both
buttons are disabled and the guard toasts "There are no runs to export yet." (`:214-217`).

The CSV writer defuses spreadsheet formula injection: a **string** cell beginning `= + - @ TAB CR`
is prefixed with an apostrophe (`:302-308`). Numbers are deliberately exempt so real figures stay
addable. The comment at `:292-301` explains that the status message is written by the pipeline and
so its first character is not ours to trust.

**States.**

| State | What is shown | Where |
|---|---|---|
| Loading | Card, "Reading the job…" | `job-assistant.html:36-37` |
| Load error | Card, alert glyph, the server's message, "Try again" -> `load()` | `:38-43` |
| Loaded, nothing asked | Card, chat glyph, "Ask about job #N, or pick a question above." | `:93-104` |
| No runs | Answers say so in words -- "This job has never run…" (`answers.ts:178`), "No run of this job has failed across N recorded runs" (`:223`) | -- |
| Exporting XLSX | The Excel button reads "Building…" with a spinning glyph; both export buttons disabled | `:27-32` |

The assistant does **not** use the shared `TableShell` chrome that gives the other 19 list screens
identical loading/error/empty states; it hand-rolls the three cards above.

**Theming and responsiveness.** Every colour is a token (`--text-secondary`, `--text-muted`,
`--color-warn-600`, `bg-subtle`, `bg-raised`, `border-subtle`), so the screen follows
`ThemeService`'s `html.dark` class (`core/theme.service.ts:16-19`) with no per-theme rules of its
own. Charts get theme-aware colours through `statusColor` (`job-assistant.ts:86`). Layout: facts
are one column below `sm`, charts one column below `lg`, the runs table scrolls inside
`overflow-x-auto` (`html:177`), presets wrap on the page and scroll horizontally in the panel
(`html:74-76`), and the panel is capped at `calc(100vw-2rem)`.

### 2.3 The server-side assistant nobody calls

`POST sourceJob.json/askAssistant` (`SourceJobRestApi.java:169-177`) and
`JobAssistantServiceImpl` (227 lines) exist, are wired into the controller's constructor

instead. `JobAssistantServiceImpl` is also on Discovery's list of seventeen service implementations
referenced by no test at all (`.ai/discovery/backend.md:1072-1079`).

## 3. Expected behaviour

Most of what the feature does today is what it should do. The differences:

**It must never answer about a job it was not given.** Today the guard is a regex and it has
bypasses -- `"explain job # 1300"` and `"summarise job 88"` both come back as an ordinary summary of
the *bound* job (issue K-1). A question that names any other job by id must be refused however the
id is written, and a question the guard cannot classify must fall to the guide rather than to a
confident answer.

**It must not refuse a question it can answer.** `OTHER_SUBJECT` refuses any question containing
"user", "account" or "tenant" (`job-assistant.intents.ts:28`), so "who is this assigned to?" phrased
as "which user owns this job" is refused -- while the Summary preset happily prints
"Assigned to <username>" from `facts.assignedUsername` (issue K-2). The rule should be about the
*subject* of the question, not about a word appearing anywhere in it.

**Silence must not be reported as fact.** When the run-history call fails the error is discarded
(`job-assistant.ts:181`) and the assistant then states "This job has never run" -- a sentence with
no support (issue K-3). For a feature whose stated value is "every number on screen is the real
one", the runs failing has to be visible.

**One assistant, not two.** Either the client's rule-based answers are the assistant and
`askAssistant` + `JobAssistantServiceImpl` are deleted, or the model path is wired up as a second
mode. Shipping an unreferenced, untested, model-calling endpoint that decrypts an API key is a
liability whichever way that decision goes (issue K-4, and §6 of the synthesis).

**Dates read the same everywhere.** "Next run" prints the raw stamp while "Last run" two rows below
it is formatted (`job-assistant.answers.ts:194` vs `:196`) -- the exact defect `humanMoment`'s own
comment says it was written to fix (issue K-5).

**The panel should be able to export.** The export buttons live in the page header, which is hidden
in compact mode (`job-assistant.html:9`), so the two panels -- the way most people reach the
assistant -- cannot download anything (issue K-7).

**It should be findable, and it should announce itself.** No nav entry, no docs mention, no
`aria-live` on the transcript, no label on the composer input, and the floating panel is not a
dialog (§13).

## 4. Frontend requirements

### 4.1 Routes

| Path | Component | Guards | Notes |
|---|---|---|---|
| `jobs/:jobId/assistant` | `JobAssistant`, lazy | `authGuard` + `passwordChangeGuard` from the shell; **no** `roleGuard`, no `minRole` | `app.routes.ts:78-82`. `jobId` arrives through `withComponentInputBinding()` (`app.config.ts:11`) |

Signed-in-only is the right floor: the two GETs behind it are `TENANT_USER`, which every signed-in
role reaches through the hierarchy (`process/src/main/java/process/config/MethodSecurityConfig.java:29`).
A `minRole: 'TENANT_USER'` on the route would match `/objects` and make the intent explicit; see the
synthesis open questions.

### 4.2 Component

`JobAssistant`, selector `app-job-assistant`.

| Input/Output | Type | Purpose |
|---|---|---|
| `jobId` | `input.required<string>()` | The job. Route-bound on the page; `String(job.jobId)` in the jobs panel (`jobs.html:450`), `jobId()` in the history panel (`job-history.html:409`) |
| `compact` | `input(false)` | Panel mode: no back link, no page head, tighter padding, presets scroll instead of wrapping |
| `closed` | `output<void>()` | Declared at `job-assistant.ts:55` and **bound nowhere** -- both panels close through their own header buttons |

Requirements that must survive any rewrite:

- Changing `jobId` must clear the transcript, the question and the runs before reloading
  (`job-assistant.ts:142-150`). The comment at `:136-141` records why: as a panel the instance is
  reused, and it once kept showing the first job it loaded, "the header naming one job while the
  answers described another."
- Only the newest in-flight load may land (`loadTicket`, `:158`).
- The microphone id must stay per-job (`:63`).
- The host must keep `.assistant-fills-panel` in compact mode, or the transcript stops scrolling
  inside the panel (`:39-45`).

### 4.3 Composer, presets and transcript

- Text input, placeholder "Ask about this job — its schedule, files, failures or history", Enter or
  the Ask button submits, Ask disabled while the trimmed question is empty
  (`job-assistant.html:52-71`).
- Microphone button only where `DictationService.supported`; while listening it is tinted
  `btn-intent-crit`, the glyph pulses, and `aria-label`/`title` switch to "Stop dictating" /
  "Listening — click to stop" (`html:59-67`).
- Six preset buttons in a fixed order -- Summary, Quick stats, Schedule, Where it writes, Failures,
  Recent runs (`intents.ts:82-89`) -- each posting its canned question straight to `askPreset`,
  bypassing `classify`.
- "Clear" appears only once there is at least one turn (`html:84-89`).
- Newest turn first. Each turn shows the question, the time as `HH:mm`, and its blocks.

**Required additions**: an accessible name on the input, `aria-live="polite"` on the transcript
container so a new answer is announced, and `Escape` closing the floating panel with focus returned
to the control that opened it.

### 4.4 States

Loading, error and empty are as in §2.1 and are adequate as page states. Two changes:

1. The runs request needs its own visible state. Answers that depend on run history must not be
   offered while it is unresolved, and must say the history could not be read when it failed.
2. The three hand-rolled cards should either move to `TableShell`'s vocabulary or be justified.
   Nineteen other screens share that chrome, and a reader who knows those screens does not know
   this one.

### 4.5 Dark and light mode

No new work: every colour is already a token, and `statusColor` supplies per-theme chart colours.
Any change must keep it that way -- no literal hex, no `html.dark` rule scoped to this feature.
Both themes need checking on the refusal paragraph, which is the only tinted text
(`--color-warn-600`, `html:124`), and on the four stat tiles, which sit on `bg-subtle`/`bg-raised`.

### 4.6 Responsive

| Width | Behaviour |
|---|---|
| `< sm` | Facts one column; presets wrap (page) or scroll (panel); runs table scrolls horizontally |
| `< lg` | Outcome donut and slowest-runs bar stack |
| Panel, any width | `w-[34rem]` capped at `calc(100vw-2rem)`; height `min(40rem, calc(100vh - 3rem))` |

The page header's two export buttons and the title share one flex row with no wrap rule; that row
should be checked at 360 px.

### 4.7 Dialogs

None today. If the panel becomes a real dialog (§13) it should use the app's existing dialog
chrome rather than a second floating-card pattern.

## 6. Database requirements

**No new tables, no new columns, no migration.** The assistant is a read over records that already
exist.

| Table | Read via | Columns it depends on |
|---|---|---|
| `source_job` | `fetchSourceJobDetailWithSourceJobId` | `job_id`, `job_name`, `job_status`, `execution`, `priority`, `last_job_run`, `assigned_user_id`, `tenant_id` |
| `scheduler` | joined into the same DTO (`SourceJobServiceImpl.java:450,590-603`) | `frequency`, `interval_value`, `start_date`, `end_date`, `start_time`, `next_run_at`, `expired` |
| `job_queue` | `fetchSourceJobQueueListWithJobId` | `job_queue_id`, `job_id`, `job_status`, `start_time`, `end_time`, `date_created`, `job_status_message` (`JobQueue.java:39-88`) |
| `source_task`, `source_task_type`, `lookup_data` | nested in the job DTO | task name, bucket, input/output folder, `service_name`, `queue_topic_partition`, pipeline and home-page lookup names |

Discovery lists `JobAuditLogs` as one of this feature's entities. **The assistant never reads it** --
it links to `/jobs/:jobId/runs/:jobQueueId/logs` (`job-assistant.html:195-196`) and lets the logs
screen do that. `Scheduler` is read and is not on Discovery's list. Both should be corrected there.

Tenancy that matters for §8: `source_job.tenant_id` is nullable and `SourceJob` declares the
Hibernate filter `tenant_id = :tenantId` (`SourceJob.java:28-29`). `job_queue`, `scheduler` and
`job_audit_logs` have **no `tenant_id` and declare no filter** (verified -- no `@Filter` in
`JobQueue.java`, `Scheduler.java`, `JobAuditLogs.java`); they inherit their tenant through the
parent job, which is the rule `V17__table_descriptions.sql:2-4` states.

## 7. Validation

| # | Rule | Client | Server | Note |
|---|---|---|---|---|
| V1 | Question must be non-empty after trim | yes -- Ask disabled (`html:68`), `ask()` returns early (`ts:187-188`) | n/a for the shipped path; `askAssistant` checks it (`JobAssistantServiceImpl.java:79-81`) | Harmless: an empty question produces no request |

| V7 | Export content ≤ 200,000 chars | **none** | yes (`FileChatServiceImpl.java:240`) | ~1,500 runs at 130 bytes a row reaches it; the user would see the server's "content too large to export." with no earlier warning |
| V8 | Export formats from a fixed set | fixed at the call site (`ts:230`) | yes (`FileChatServiceImpl.java:245-249`) | |
| V9 | CSV cells starting `= + - @` are neutralised | **yes** (`answers.ts:302-308`) | no | Client-only, and correctly so: the CSV is built in the browser and never round-trips as CSV. Covered by `csv-injection.spec.ts` |

**Client-only rules are V2, V3, V6 and V9.** V3 is the notable one. It is client-only and cannot be

the scope guarantee rests entirely on one regex file, which is exactly why K-1 matters.

## 8. Security

### 8.1 Layer by layer

| Layer | What it does here | Verdict |
|---|---|---|
| **Frontend guard** | `authGuard` + `passwordChangeGuard` from the shell (`app.routes.ts:46-52`). No `roleGuard`, no `minRole` on the assistant route (`:78-82`) | Correct floor, but implicit. Nothing renders that a `TENANT_USER` may not have |
| **Controller `@PreAuthorize`** | `hasRole('TENANT_USER')` at class level on `SourceJobRestApi` (`:28`) and `FileChatRestApi` (`:22`). No method-level override on any of the four endpoints | Correct. `PLATFORM_ADMIN > TENANT_ADMIN > TENANT_USER` (`MethodSecurityConfig.java:29`, pinned by `MethodSecurityConfigRoleHierarchyTest`) means all three roles reach them |
| **Service rule** | `SourceJobServiceImpl.isOwnedByCaller` -> `TenantOwnership.isOwnedByCaller` (`:104-106`) on both reads. `JobAssistantServiceImpl` has its **own copy** (`:118-123`) that omits the null-caller test | **The one defect.** See K-4a |
| **Hibernate `@Filter`** | `tenantFilter` enabled by `TenantFilterHelper.enableIfNeeded` before each read. `SourceJob` declares `tenant_id = :tenantId` (`SourceJob.java:28-29`); `JobQueue` and `Scheduler` declare **nothing** | Contributes almost nothing here. Both reads use `findById`, which the filter does not touch, and the runs are read off an unfiltered entity. The service rule is the whole boundary |

The last row is the point. Two of this feature's three reads reach a row by primary key, and the
third reads an entity that has no filter to apply, so **every isolation guarantee in this feature is
the service check and nothing else.** Getting it wrong is not caught anywhere downstream.

### 8.2 Per role

| Role | May do |
|---|---|
| `TENANT_USER` | Open the page and both panels for any job in **its own tenant**; ask, export CSV and XLSX. A job in another tenant, a platform-owned job (`tenant_id IS NULL`) or a `Delete` job returns `status: ERROR, "SourceJob not found with N."` on both reads, and the screen shows that message with a retry button |
| `TENANT_ADMIN` | Exactly the same. The assistant is a read; nothing here is admin-gated at any layer |
| `PLATFORM_ADMIN` | Every job in every tenant, including platform-owned ones (`TenantOwnership.isOwnedByCaller` returns true immediately, `TenantOwnership.java:36-38`) |
| A caller carrying **no tenant** and not `PLATFORM_ADMIN` | Nothing, on the two reads: `TenantOwnership` refuses a null caller outright (`:39-40`, pinned by `TenantOwnershipTest.aCallerWithNoTenantOwnsNothing`). But **`askAssistant` grants it every platform-owned job** -- K-4a |

The refusal message deliberately does not distinguish "does not exist" from "not yours"
(`SourceJobServiceImpl.java:452,462`, and the same wording is copied into
`JobAssistantServiceImpl.java:86-88` with a comment saying so).

### 8.3 What the assistant can and cannot leak

It cannot leak another job's data, because no other job's data is ever fetched: the two GETs are
keyed on the bound `jobId` and both are ownership-checked. A scope-guard bypass (K-1) produces a
**mislabelled** answer -- the bound job's figures under a question naming another job -- which is a
correctness and trust defect, not a cross-tenant one. That distinction should be preserved by any
fix: the guard is about not misleading the reader, and the server check is about isolation.

`askAssistant` is different. It sends one job's full record, schedule, failure messages and 40 runs
to a third-party model endpoint, and decrypts a stored API key to do it
(`AiAgentServiceImpl.java:245-247`). That path is unreferenced, untested and carries the broken
ownership copy.

## 12. Known issues

### K-1 -- The scope guard has bypasses that produce a confident wrong-labelled answer

`OTHER_JOB_ID = /(?:job\s*#?|#)(\d{3,})\b/i` (`job-assistant.intents.ts:25`). Running `classify`
exactly as written, bound to job 1244:

| Question | Result | Should be |
|---|---|---|
| `explain job # 1300` | `{intent:'summary'}` | `out-of-scope` |
| `summarise job 88` | `{intent:'summary'}` | `out-of-scope` |
| `what does job 88 write?` | `{intent:'target'}` | `out-of-scope` |
| `what about jobs 1300 and 1301` | `{intent:'unknown'}` | `out-of-scope`, naming 1300 |

The first is the sharp one: `job\s*#?` allows whitespace *before* the hash but not after it, so a
space after `#` slips the guard entirely and job 1244's summary is printed under the question
"explain job # 1300". Severity is bounded -- no other job's data is fetched, so this mislabels
rather than leaks -- but for a feature sold on "it cannot be talked into discussing another job"
this is the failure mode that matters. The `\d{3,}` floor is largely covered in practice by
`SourceJob`'s sequence starting at 1000 (`SourceJob.java:47-53`), so live ids are four digits; the
`# ` case is not covered by anything. `chatbot-suite.spec.ts:34-47` tests ten adversarial phrasings
and none of them is these.

### K-2 -- Questions the assistant can answer are refused because of one word

`OTHER_SUBJECT = /\b(users?|tenants?|organisations?|organizations?|accounts?)\b/i`
(`job-assistant.intents.ts:28`) is tested against the whole question before any intent pattern
(`:64`). Verified against the real regex, bound to 1244:

- `which user owns this job` -> `out-of-scope`
- `what is the assigned user` -> `out-of-scope`
- `does it write the accounts file` -> `out-of-scope`

Meanwhile the Summary answer prints `{ label: 'Assigned to', value: facts.assignedUsername }`
(`job-assistant.answers.ts:167`) -- the assistant refuses to answer a question whose answer it
volunteers one click away. The third case refuses a plain storage question because a folder happens
to be called "accounts".

### K-3 -- A failed run-history load is reported as "this job has never run"

`job-assistant.ts:175-182`:

```ts
error: () => { /* the assistant still answers what it can without run history */ },
```

`loading` is driven only by the detail request (`:166`), and `runs` was set to `[]` by the effect
(`:148`). So when the queue call 500s the screen looks fully loaded and then states, from
`job-assistant.answers.ts:178`, "This job has never run, so there is nothing to count yet." The
stat tiles show 0 and a `—` success rate; Failures says "No run of this job has failed across 0
recorded runs." The comment's intent is reasonable -- keep answering the schedule and storage
questions -- but the run-derived answers must not be offered as facts when the runs are unknown.
This is the one defect that contradicts the component's own premise at `job-assistant.ts:32-33`.

### K-4 -- A model-calling endpoint that nothing calls, untested, with its own ownership rule

`POST sourceJob.json/askAssistant` (`SourceJobRestApi.java:169-177`) and
`JobAssistantServiceImpl` (227 lines) are wired and reachable. `askAssistant` returns **zero**
matches across `scheduler1/next` (excluding `node_modules`) and zero across `scheduler1/src`.
Discovery lists it as this feature's endpoint. It is one of seventeen service implementations with
no test at all (`.ai/discovery/backend.md:1072-1079`).

**K-4a, the security half.** `JobAssistantServiceImpl.java:118-123` keeps a private copy of the
ownership rule:

```java
private boolean isOwnedByCaller(SourceJob job) {
    if (TenantContext.isPlatformAdmin()) { return true; }
    return job != null && Objects.equals(job.getTenantId(), TenantContext.getTenantId());
}
```

The canonical rule is `TenantOwnership.isOwnedByCaller` (`process/src/main/java/process/security/TenantOwnership.java:35-41`),
which the copy differs from in exactly one clause -- `callerTenantId != null`. For a caller whose
`TenantContext.getTenantId()` is null and whose role is not `PLATFORM_ADMIN`, `Objects.equals(null,
null)` is `true`, so **every platform-owned job (`tenant_id IS NULL`) is served.**
`TenantFilterHelper.enableIfNeeded` makes this reachable rather than theoretical: with a null tenant
it *disables* the filter (`TenantFilterHelper.java:28-33`), so nothing downstream catches it -- and
`findById` would not have been filtered in any case.

`app_user.tenant_id` is nullable (`AppUser.java:56-57`; `.ai/discovery/database.md:236-238`) and
`source_job.tenant_id` is nullable with an explicit backfill for null rows
(`.ai/discovery/database.md:236-238, :240-243`), so both halves of the fixture exist. This is the precise case
`TenantOwnership`'s own javadoc says the private copies had drifted on
(`TenantOwnership.java:6-8`), and that `TenantOwnershipTest.aCallerWithNoTenantOwnsNothing`
(`process/src/test/java/process/security/TenantOwnershipTest.java:66-73`) exists to prevent. That
test does not reach `JobAssistantServiceImpl`, which is why the regression survived.

### K-5 -- "Next run" prints a raw timestamp beside a formatted "Last run"

`job-assistant.answers.ts:194` vs `:196`:

```ts
rows.push({ label: 'Next run', value: s.expired ? 'Expired — no further runs' : (s.nextRunAt ?? 'Not scheduled') });
if (facts.lastJobRun) rows.push({ label: 'Last run', value: humanMoment(facts.lastJobRun) });
```

`Scheduler.nextRunAt` is a `LocalDateTime` (`process/src/main/java/process/model/pojo/Scheduler.java:79`)
serialised as an ISO string, so the Schedule answer shows `2026-09-01T09:00:00` on one row and
`19 Aug 2026, 00:01` on the next. Every other screen formats it -- `jobs.html:195`,
`job-history.html:97`, `query-engine.html:89` all pipe it through `date:'d MMM, HH:mm'`. This is the
same defect `humanMoment`'s comment (`answers.ts:102-107`) says it was written to fix; the fix was
applied to `lastJobRun` and not to `nextRunAt`. The `Starts` row (`:192`) is raw too, though a
`LocalDate` reads acceptably as `2026-09-01`. No test covers the Next run row's format --
`job-assistant.intents.spec.ts:185-191` asserts Last run only.

### K-6 -- `askAssistant` will discuss a deleted job

Both reads refuse a job in `Status.Delete` (`SourceJobServiceImpl.java:447` and `:467-469`, the
latter with a comment explaining that serving its runs "would be the one place it survived").
`JobAssistantServiceImpl.ask` checks presence and ownership (`:84-89`) and never looks at
`jobStatus`, so it will hand a deleted job's name, task, schedule, failure messages and 40 runs to a
model. Currently unreachable because nothing calls the endpoint; it becomes live the moment K-4 is
resolved by wiring rather than deleting.

### K-7 -- The panels cannot export

The CSV and Excel buttons live inside `div.page-head`, which carries
`[class.hidden]="compact()"` (`job-assistant.html:9`, buttons at `:22-32`). Both panels pass
`compact=true`, so the export exists only on the full page. Since the panels are how the feature is
reached from the jobs list and from run history, most users never see the export at all.

### K-8 -- Dead output

`readonly closed = output<void>()` (`job-assistant.ts:55`), documented as panel-close plumbing.
Grepping `(closed)` across `src/app` finds one binding and it is the file chat's
(`features/objects/objects.html:282`). Both assistant panels close through their own header buttons
(`jobs.html:439`, `job-history.html:403`). Harmless, misleading to the next reader.

### K-9 -- Zero tests below the two pure modules

75 assistant tests, all against `job-assistant.intents.ts` and `job-assistant.answers.ts`. No spec
imports the component (verified). Consequently nothing covers: the two HTTP calls and their error
paths, the `loadTicket` race, the transcript reset on `jobId` change (a bug the code comments say
was already hit once, `job-assistant.ts:136-141`), `exportRuns` in either format, the panel wiring
in `jobs.ts`/`job-history.ts`, or the route. On the server, `JobAssistantServiceImpl` has no test at
all while every comparable service has a `*TenantIsolationTest`
(`process/src/test/java/process/model/service/impl/` lists thirteen of them) -- and it is the one
whose ownership rule regressed.

### K-10 -- Two answers make ordering claims they do not enforce

`answerFor('history')` returns `[...runs].slice(0, 15)` under the sentence "N runs recorded, most
recent first" (`job-assistant.answers.ts:244-246`), and `failures` slices ten
(`:235`), both without sorting. They are correct only because
`fetchSourceJobQueueListWithJobId` sorts by `dateCreated` descending
(`SourceJobServiceImpl.java:472`). A pure function that asserts an order its caller supplies is one
API change away from being wrong, and no test pins it.

### K-11 -- `slowestRuns` does not reject a negative duration

`job-assistant.ts:121-130` computes `end - start` with no `>= 0` guard, while `computeStats`
(`answers.ts:77`) has one and `chatbot-suite.spec.ts:103-108` pins that behaviour. A run whose end
precedes its start therefore contributes a negative bar value. In practice it sorts to the bottom
and is dropped by `.slice(0, 6)`, so the visible effect is nil unless a job has fewer than six timed
runs -- in which case `humanDuration` renders something like `-3600s`. Cosmetic, listed because the
two duration calculations disagree and only one of them is tested.
