## .ai/spec/04-STORAGE-INTEGRATION.md and .ai/spec/05-DUCKDB-INTEGRATION.md (audited against process/src/main/java/process/analytics/, process/src/main/java/process/api/Analytics*.java, process/src/main/java/process/model/service/ObjectStorageService.java + impls, process/src/test/java/process/analytics/, scheduler1/next/src/app/features/analytics/, and the design record in .ai/grooming/analytics-studio.md)

Three things dominate. (1) Analytics does not use the platform's ObjectStorageProvider abstraction for anything that matters: of the 6 contract operations, only listContainers and listObjects are actually exercised by the module (through the Object Browser's own UI service), getMetadata is reached from one PLATFORM_ADMIN endpoint that has no frontend at all, exists() does not exist anywhere in the platform, and both openStream and write are bypassed — DuckDB opens its own HTTP stream via httpfs and writes back with its own COPY (AnalyticsQueryService.java:386-388). Spec 04's "generated output is written through the same provider abstraction" is therefore not satisfied, and it cannot be satisfied by flipping a flag: writableUrl hard-codes "s3://" (AnalyticsQueryService.java:466-468). (2) Azure is not reachable — it is refused by name at DatasetResolver.java:114-117 before it can reach the engine, and greyed out in the picker at analytics.ts:361-362. The code branch exists (DuckDbSessionFactory.java:130-134, azureSecret :178-186) and has never been run; the design record states this deliberately (grooming A16, .ai/grooming/analytics-studio.md:1165-1178). The spec's "S3, MinIO AND Azure adapters" and that recorded decision cannot both be satisfied today — one of them has to move. Worse for the spec than the docs admit: the live verification was against MinIO only (grooming :776-777), so the AWS-S3 branch of s3Secret (the blank-endpoint, virtual-host path at DuckDbSessionFactory.java:167-174) is also unexercised, while DatasetResolver.java:116 tells the user "S3 and MinIO have been [verified]". (3) There is no cancellation and no AnalyticsEngine. A user cannot stop a running query: the only cancel() in the module is the server-side timeout watchdog (AnalyticsQueryService.java:920-940), there is no endpoint, no query handle, and no UI control. Of the six lifecycle states the spec names, only two exist in any form (SUCCESS, FAILED), with a third the spec never names (REFUSED) doing most of the work; QUEUED, RUNNING, CANCELLED and TIMED_OUT are absent, and a timed-out query is recorded as REFUSED (AnalyticsRestApi.java:229). DuckDB is named directly in every class in the package — no interface exists in process/src/main/java/process/analytics/ at all, and "AnalyticsEngine" appears nowhere in process/src.


**Conflicts and things the spec does not settle.**

1) 04 requires an Azure Blob adapter; the design record (.ai/grooming/analytics-studio.md:1165-1178, A16, restated as open item 5 at :1308) records a deliberate decision that Azure must not be offered until it has been run against a real container, and the code implements that decision as a hard refusal (DatasetResolver.java:114-117) with a test pinning the message word-for-word (DatasetResolverTest.java:251-265). Both can be satisfied, but only by doing the verification and deleting the gate — the reconciliation is a container, a connection string and one read, not a code change. Relaxing the gate without verifying would reinstate exactly the failure A16 predicts (an unmapped engine error landing on "The dataset could not be read"), and would also hit a second, undocumented wall: write-back would still refuse every Azure target because writableUrl hard-codes s3:// (AnalyticsQueryService.java:466-468).

2) The design record contradicts itself about S3. Grooming :776-777 states that everything marked verified "was observed through the real API and the real UI against MinIO"; grooming :1173 states "S3 and MinIO share the S3 protocol and were both verified". Those cannot both be true, and the code takes the second reading into a user-facing sentence: DatasetResolver.java:116 tells a user "S3 and MinIO have been [verified]". s3Secret's endpoint-present branch (DuckDbSessionFactory.java:167-174) is the MinIO path; a real AWS connection with a blank endpoint skips it entirely, so the branch AWS would take is unexercised. By the module's own honesty rule this message is an overclaim of the same kind the Azure gate exists to prevent.

3) 05 requires an AnalyticsEngine abstraction; 04's read strategy requires "DuckDB-compatible remote access" and 05's file access requires resolving into "a safe DuckDB relation/view" — the spec names the engine in the requirements that are supposed to be engine-agnostic. The built module resolved this in DuckDB's favour throughout, and the design docs never record the trade-off, so this is a spec-internal tension that was never surfaced.

4) 05's lifecycle (QUEUED → RUNNING → …) presumes asynchronous, addressable query execution; every analytics endpoint is synchronous and blocking (AnalyticsRestApi.java:186-241), and AnalyticsQueryService.java:85-88 records a deliberate decision not to queue ("fail fast while the user is still looking at the screen"). CANCELLED and the QUEUED/RUNNING states are not separately buildable — they need the same missing piece, an in-flight registry plus a handle returned to the client, which is an architectural change to the request model rather than four new enum values.

5) 05's "cancellation" under Safety and 04's "generated output written through the same provider abstraction" both depend on execution-model detail that 03-END-TO-END-FLOW would plausibly have settled (whether a query is a request or a job; whether write-back is an analytics action or a platform storage action). That document is referenced by 00-MASTER-INDEX.md but was never provided, so I am flagging the dependency rather than assuming what it said.

## .ai/spec/07-ANALYTICS-CANVAS.md (the Analytics Canvas — dimensions, measures, filter builder, cross-filtering, drill-down/up, pivot, Top-N, saved analysis, safe query generation), cross-checked against .ai/spec/09-API-CONTRACTS.md and .ai/spec/10-DATABASE-MODEL.md, the built process/analytics + process/api backend, scheduler1/next/src/app/features/analytics/, scheduler1/next/src/app/shared/charts/, scheduler1/next/src/app/features/reports/, and the module's own design record (.ai/synthesis/analytics-studio.md, .ai/grooming/analytics-studio.md).

Document 07 was not built. Not partially, not in a different shape — the structured analysis model it specifies does not exist anywhere in the codebase. There is no dimension, no measure, no filter, no drill, no pivot and no top-N concept in process/analytics/ (15 files, 4049 lines), in the four Analytics REST controllers, in the three changelogs, in the 11 backend test classes, or in features/analytics/ (analytics.ts, .html, .service.ts). What was built instead is a SQL console: five tabs — Overview, Data, Profile, Quality, SQL (analytics.ts:42, :447-453) — where a user types a statement into CodeMirror and StatementGate decides whether DuckDB will run it. Every capability in this document can be hand-computed by someone who writes the GROUP BY themselves, and that is explicitly not the requirement: spec 09 defines POST /analytics/analyze, /analyze/drill and /analyze/drill-up with a typed {dimensions, measure, aggregation, filters, limit} body (09-API-CONTRACTS.md:17-19), and spec 10 defines an analytics_analysis table to hold "structured dimension/measure/filter configurations" (10-DATABASE-MODEL.md:41-42). Neither endpoint nor table exists. So this is MISSING, not PARTIAL, all the way down.

The most important thing here is the reuse candidate, and it is a strong one. /reports already contains a working pivot engine over a different data source: six dimensions (pivot.ts:73-81), sixteen measures including count, distinct, sum, avg, median, min, max and p90/p95/p99 (pivot.ts:107-121, aggregate() at :180-220), a row × column matrix with row/column/grand totals (buildPivot at :237-262), click-any-cell drill-through to the underlying rows (report-pivot.ts:241-256), ten chart kinds, an additivity gate that stops a donut of averages (pivot.ts:133), and removable filter chips over five equality filters plus a date range (reports.ts:123-165, reports.html:104-119). That is roughly half of document 07 already written and tested — but over a fixed RunData shape: job_queue runs, dictionary-encoded, seven fixed columns, all grouping done in the browser on rows fetched whole by GET /report.json/runs (ReportRestApi.java:39, pivot.ts:10-46). An analytics dataset has arbitrary columns of arbitrary types and cannot be fetched whole. The module's own design record already argued this out and reached the same place: synthesis/analytics-studio.md:688-710 records Q2 — "should Analytics Studio's charts land in the existing /reports pivot" — as "the most consequential open question in this document and it is not settled", with option (b), generalising the pivot, called "the right long-term answer and the wrong immediate one".

Third thing, and it is a process finding worth flagging: the analytics chart block shipped anyway. The design record's own sequencing rule says "Gap 29 must not start until Q2 is answered" (synthesis:623); gap 29 is marked "Done 2026-09-08" (synthesis:108) while Q2 is still recorded as undecided, and analytics.html:835-970 now holds a second chart builder (label column, value column, four kinds) beside the reports one. So the console has begun acquiring the two charting systems Q2 exists to prevent, before the question that governs document 07's whole implementation shape was answered. Whoever builds the canvas should answer Q2 first, because the answer decides whether this is one large build or a generalisation of code that already works.


**Conflicts and things the spec does not settle.**

Four, in descending order of how much they should change a plan.

1. The platform's own safety gate blocks the most direct route to the pivot requirement. Spec 07:81-82 requires "row dimension × column dimension with aggregation in cells". DuckDB has a PIVOT statement; StatementGate deliberately refuses it — "What it refuses that somebody may reasonably want... PIVOT and UNPIVOT, which are reads that DuckDB declines to serialise, so they arrive here indistinguishable from a write" (StatementGate.java:57-59). This is not an argument against the requirement, it is a constraint on the implementation: the pivot must be built from conditional aggregation or a plain GROUP BY pivoted client-side (which is what report-pivot.ts already does), or StatementGate needs a named exception, which reopens the safety case the whole module rests on. Nothing in spec 07 acknowledges this and it is the kind of thing that gets discovered three days into the build.

2. Spec 07 asks for a second interactive analysis surface; the master index (00-MASTER-INDEX.md, "Agent rule") says "Reuse existing storage, authentication, scheduler, Kafka, database, UI, charts, tables... Do not build parallel infrastructure." Those two pull opposite ways once /reports is on the table, and the design record's Q2 is exactly this tension left undecided. The spec never mentions /reports; the reuse question is answerable only from the codebase.

3. Cross-filtering has no target to filter. Spec 07:60-68 requires that clicking a result filters "data table", "other compatible charts" and "KPI cards"; spec 06's Interaction principle repeats it. But the Data tab is a plain paged table with no filter, no sort, no search and no column controls (analytics.html:244-274), the preview endpoint takes only connection/path/page/size (AnalyticsRestApi.java:118-130, AnalyticsQueryService.preview:216/:235), the header strip is dataset metadata rather than KPI cards and deliberately so (analytics.html:154-157), and the module documents that the preview has no ORDER BY on purpose because object storage has no row order (analytics.html:294-296, AnalyticsQueryService.java:100-101). So cross-filtering depends on filterable-table work that spec 06 owns and that also is not built. This dependency is not stated in either document, and it is the kind of sequencing 03-END-TO-END-FLOW would plausibly have carried — that document is referenced by the index and was never provided, so I am naming the dependency rather than assuming what it said.

4. Provider scope, which silently bounds every item below. DatasetResolver refuses AZURE outright with "Analytics Studio has not been verified against Azure Blob yet" (DatasetResolver.java:114-118). Spec 07 assumes a dataset is readable; in practice anything built here will work for S3 and MinIO and be refused for Azure until somebody verifies that branch. Not a contradiction inside document 07, but every effort estimate below is for an S3/MinIO-only feature.

## .ai/spec/10-DATABASE-MODEL.md and .ai/spec/11-SECURITY-MULTITENANCY.md (repo root /Users/nabeel.amd93/Desktop/Old-School)

Three things dominate. (1) Of the seven tables the spec names, four exist as DDL and only three are actually read and written; analytics_dataset is a complete dead limb — changeset V31, entity, and repository all exist, and no service, controller, or frontend file in the repository injects AnalyticsDatasetRepository or constructs an AnalyticsDataset (grep over process/src/main returns zero hits outside the entity and repository themselves). analytics_analysis, analytics_dashboard and analytics_dashboard_widget do not exist in any form. (2) Of the spec's seven audit events, exactly ONE writes a durable record: "query executed" (and, inside that same path, a permission failure on /analytics.json/query, recorded as run_status REFUSED). "Dataset opened", "profile requested", "export requested" and "output written" write a logger.info line and, for the two export paths, a fire-and-forget Kafka event on a bounded queue that drops under load — neither is durable, and the code's own comments say so ("this is the only durable record that a copy of somebody's data left the application" is describing a log line). "Dashboard changed" has nothing to record. Role-level permission failures reach GlobalExceptionHandler and produce one logger.warn that names neither the user nor the endpoint. (3) The abuse-control requirement is half met and the halves are not interchangeable: a JVM-wide fair Semaphore caps concurrent queries at 4 and is genuinely enforced, but there is NO rate limiter anywhere — grep for ratelimit/throttle/bucket4j over process/src/main returns nothing. Nothing bounds how many queries one caller may fire per minute, only how many may be in flight at once. Separately worth flagging: the tenant-isolation code is the strongest part of the module. The Hibernate-@Filter-does-not-apply-to-findById trap is explicitly identified and handled — AnalyticsQueryRepository declares findByAnalyticsQueryId (a query, so the filter applies) instead of findById, and AnalyticsQueryLibraryServiceImpl.scopedFind re-checks ownership on top of it. DatasetResolver uses isOwnedByCaller (not the looser isVisibleToCaller), refuses absent and forbidden connections with an identical message, and DatasetRef's only constructor is package-private with DatasetResolver its sole caller in main.


**Conflicts and things the spec does not settle.**

1. Table naming: spec 10 names analytics_saved_query and analytics_query_history; the build ships analytics_query and analytics_query_run. Functionally equivalent, but no design doc records the rename, so a reader following the spec will not find the tables.

2. Dashboards, spec vs. recorded decision: spec 10 requires analytics_dashboard and analytics_dashboard_widget, and spec 11 requires a "dashboard changed" audit record. The design record deliberately refuses to build them and says why — /Users/nabeel.amd93/Desktop/Old-School/.ai/synthesis/analytics-studio.md:689-704 raises "should Analytics Studio's charts land in the existing /reports pivot rather than becoming a second dashboard system?" as "the most consequential open question in this document and it is not settled. The user has been warned about it and has not decided." Building the spec's two dashboard tables would settle that question by accident. This is a genuine spec-vs-design conflict that needs a human decision, not an implementation task.

3. Spec 11's data-leakage clause assumes a shape the API does not have: "Never allow a user to reference another tenant's dataset ID by guessing an identifier." There is no dataset ID on the wire anywhere in this module — every endpoint takes a connection alias plus a path and re-resolves both per request. The requirement is satisfied, but by a stronger mechanism than the one it describes; if analytics_dataset is ever wired up and dataset IDs start appearing in requests, this clause becomes live and currently has no enforcement written for it.

4. Spec 10 asks analytics_query_history for "bytes_scanned if available". Nobody appears to have established whether duckdb_jdbc 1.1.3 exposes it. There is no note in V32__analytics_query.sql, in the synthesis, or in the grooming doc either way — so the "if available" escape hatch has not been evaluated, it has been skipped.

5. Master index agent rule ("Reuse existing storage, authentication, scheduler, Kafka, database, UI... Do not build parallel infrastructure") vs. the audit gap: the platform already has audit infrastructure — /Users/nabeel.amd93/Desktop/Old-School/process/src/main/java/process/util/OpenSearchAuditLogClient.java, used by SourceJobServiceImpl, TransactionServiceImpl and AuditLogSyncCron, plus a JobAuditLogs entity. Analytics uses none of it, and instead has its own single-purpose analytics_query_run table plus log lines. Whether that is the right call is arguable, but no design doc argues it.

6. 03-END-TO-END-FLOW is absent, as the task notes. Spec 11's audit list uses two terms — "dataset opened" and "output written" — that are golden-workflow step names from the master index rather than anything defined in 10 or 11. I have audited them against the obvious code paths (/schema+/preview+/profile for "opened", writeBack for "output written"), but the exact boundary of each event is defined, if anywhere, in the missing document.

7. Grooming doc is stale relative to the code on one security-relevant point: /Users/nabeel.amd93/Desktop/Old-School/.ai/grooming/analytics-studio.md:V6 row records DatasetResolver as using TenantOwnership.isVisibleToCaller. The current code uses isOwnedByCaller (DatasetResolver.java:90), which is stricter and correct. Not a conflict in the code, but a reader trusting the grooming doc will be misled about both.

## .ai/spec/01-DISCOVERY-ARCHITECTURE.md, .ai/spec/02-PRODUCT-REQUIREMENTS.md, .ai/spec/06-DATASET-WORKSPACE-UX.md — audited against scheduler1/next/src/app/features/analytics/ (analytics.ts 1971 lines, analytics.html 1121 lines, analytics.service.ts 378 lines), scheduler1/next/src/app/shared/ui/data-table.ts, scheduler1/next/src/app/features/objects/storage.service.ts, and the backend surfaces they call (process/src/main/java/process/analytics/, process/src/main/java/process/api/Analytics*RestApi.java, process/src/main/resources/db/changelog/changelog-sets/V31–V33).

Five tabs shipped where the spec names ten. `type Tab = 'overview' | 'data' | 'profile' | 'quality' | 'sql'` (analytics.ts:42) — Compact, Columns, Analytics, Charts and Activity have no tab. Two of those five absences are relocations with a written reason (Charts sits under the SQL result, Columns became a rail beside the Data grid), one is a rename (Details → Overview), and two are genuinely unbuilt: Compact does not exist in any form, and Analytics — 07's whole dimension/measure/drill-down/cross-filter layer — has not a single line of code on either side of the wire. Second: the Data view is a read-only page-turner, not a grid. Of 06's eight named grid capabilities exactly two are built (pagination, horizontal scroll); sorting, filtering, search, column resize, column visibility and copy-cell are all absent, and only sorting has a recorded reason. Third, and the one I would put at the top of a fix list: 06's "Interaction principle" — any summary value clickable, clicking creates a filter — is not implemented anywhere. `grep -n "(click)"` over the whole 1121-line template returns 23 handlers and every one is navigation, paging, a form control or a library action; no figure, bar, quartile block, chart mark or quality finding is clickable. There is no filter model in the component at all (no `addFilter`, no `datasetFilter`, no drill state), so 06's interaction principle, and with it 02's advanced filters, drill-down/drill-up and cross-filtering, are one shared hole rather than four independent ones. Separately: the `analytics_dataset` table (V31) is dead — `AnalyticsDatasetRepository` is referenced by nothing but its own declaration, so nothing in the product registers, saves or lists a dataset. 01's non-negotiables come off well: no credentials reach the browser (BucketSummary carries label/bucket/provider and nothing else), no dataset rows are copied into PostgreSQL (all three changelog tables are metadata-only), Kafka and the scheduler are reused not duplicated. The one non-negotiable that is not clean is "no provider-specific analytics code": DuckDbSessionFactory switches on StorageProvider and decrypts connection secrets itself rather than going through 04's storage abstraction.


**Conflicts and things the spec does not settle.**

Three, plus one missing document.

1. 03-END-TO-END-FLOW is referenced by 00-MASTER-INDEX's required document order and was never provided. Two things in my area depend on it and I have not judged them: (a) the master index's golden workflow names "dataset registration" as a step, and V31 creates `analytics_dataset` to hold one, but no service, endpoint or UI writes or reads that table (`grep -rn "AnalyticsDatasetRepository" process/src scheduler1/next/src` returns only process/src/main/java/process/model/repository/AnalyticsDatasetRepository.java:12). Whether registration was meant to be a distinct user step or is satisfied by opening a file ad-hoc is exactly what 03 would say. (b) The golden workflow also names "dashboard" between chart and export; nothing named dashboard exists in the analytics module. I am reporting the table as dead code and the capability as MISSING rather than inventing the flow.

2. 02 requires "any authorized S3, MinIO or Azure connection" and 04 requires an Azure Blob adapter; the build refuses Azure on both sides on purpose. DatasetResolver.java:114-116 throws "Analytics Studio has not been verified against Azure Blob yet", and analytics.ts:363-364 greys the option out with the same sentence. The reason is recorded at DatasetResolver.java:101-113: the Azure branch in DuckDbSessionFactory (:130-133, azureSecret :178-184) was written from documentation and never run against a real container. This is a deliberate honesty gate rather than an oversight, but it means a stated MVP provider is refused, and the spec has no "verified providers only" clause to hang it on.

3. 06 says the Profile view shows "aggregate distributions and data-type summaries" and the Columns view shows the ~14 per-column statistics. The build inverts this: the tab labelled Profile renders per-column cards (analytics.html:351-489), i.e. 06's Columns view, and there is no aggregate view of any kind. So "Profile" as a name is present while "Profile" as 06 defines it is absent — a reader checking the tab strip against 02's list would score this DONE and be wrong.

4. Documentation drift, not a spec conflict, but it will mislead the next audit: .ai/synthesis/analytics-studio.md:102 (gap row 23) states "**No database change at all.** No AnalyticsDataset, SavedQuery, QueryHistory, Dashboard or BenchmarkResult entity exists", and :69 states rows 23-33 are "none of them started". That is stale — V31/V32/V33 exist and AnalyticsQuery, AnalyticsQueryRun and BenchmarkResult are all wired to live services. Only the AnalyticsDataset half of that sentence is still true. Do not read that document as a statement of current state.

## .ai/spec/08-SQL-STUDIO.md and .ai/spec/09-API-CONTRACTS.md, audited against the code under /Users/nabeel.amd93/Desktop/Old-School (process/src/main/java/process/analytics, process/src/main/java/process/api, process/src/main/resources/db/changelog, scheduler1/next/src/app/features/analytics, scheduler1/next/src/app/shared/ui/data-table.ts) and against the module's design record in .ai/synthesis, .ai/grooming and .ai/execution.

Three things dominate. (1) The SQL console is real and the security half of doc 08 is genuinely done — a locked-down session, a parser-based statement gate that walks all three name parts, per-dataset tenant resolution for both sides of a join, and an audit row written for successes, failures and refusals alike. What is missing is the whole "operating a long query" half: there is no cancel anywhere in the system (no endpoint, no in-flight registry, no client call), no formatting, no execution time on the result, and no server pagination, column resize or sorting on the SQL result grid — that grid is a plain <table> inside a 96-line shell with no such code in it. Of the six query states the spec names, three exist (Running as a UI boolean, Completed, Failed); Draft and Cancelled do not exist at all, and Timed Out exists as a real server-side stop but is recorded and displayed as "refused", so it is not distinguishable from a governor rejection in the audit trail. (2) The editor is CodeMirror 6, not Monaco — a defensible swap, but the deviation is nowhere recorded: .ai/ contains no occurrence of "CodeMirror" as a decision, and three separate design documents still say the editor choice is open. (3) Doc 09's biggest holes are structural, not cosmetic: there is no dataset registration or listing API at all (the V31 analytics_dataset table is written by nothing — AnalyticsDatasetRepository has zero callers), the entire /analyze, /analyze/drill and /analyze/drill-up surface does not exist, export is synchronous base64 with no artifact to fetch, and the query response carries no id, no timing, and column NAMES only — the types are read off ResultSetMetaData and thrown away one line later. Correlation IDs do not exist anywhere in the backend.


**Conflicts and things the spec does not settle.**

Four conflicts, plus one dependency on the missing document.

1. 09 presumes correlation IDs already exist ("Use existing API error envelopes and correlation IDs"). The envelope exists (ResponseDto, used consistently). Correlation IDs do not exist anywhere in this codebase — no MDC, no X-Request-Id, no traceId in process/src/main/java. So half that sentence is a reference to a platform feature and the other half is net-new cross-cutting work that doc 09 does not scope.

2. 09's dataset endpoints are keyed by {id}; the module's central, deliberately-recorded security property is that a dataset is named by connection alias + path and never by an id, a bucket or a URL (process/src/main/java/process/api/AnalyticsRestApi.java:33-38, with the mid-build change from storageConnectionId+bucket+path recorded at .ai/execution/README.md:135). Introducing dataset ids is therefore not a rename — it requires a registry, and the registry table that was built for it (V31 analytics_dataset) is currently written by nothing. Whoever schedules this should decide whether an id is wanted at all, or whether alias+path is the answer and doc 09's /datasets rows should be rewritten.

3. 08 names Monaco; the project's own design record argues against it (.ai/synthesis/analytics-studio.md:669-686 — ~2 MB, would be the largest single frontend dependency, "no recommendation yet... this wants a decision from whoever owns the bundle budget"). The build shipped CodeMirror 6 and never wrote the decision down, so the spec, the design record and the code now say three different things.

4. 08 asks for server pagination on the SQL result grid; the module's execution design is a single-shot query capped by analytics.query.max-rows with truncation as a headline claim (AnalyticsQueryService.java:317-321). Paging arbitrary user SQL needs either a stable ORDER BY — and the project already records that object storage has no natural row order, which is why even the preview's paging is only as stable as the reader's own ordering (.ai/execution/README.md:135) — or a materialised result set with a lifetime and an id. Neither is designed anywhere, and the choice interacts with /export/{id} and /query/{id}/cancel, which need the same "a run is a durable thing with an id" concept.

Dependency on the missing 03-END-TO-END-FLOW: 08 lists six query states (Draft, Running, Completed, Failed, Cancelled, Timed Out) but never says who sets them, where they live, or what the transitions are. Three of the six are absent and one (Timed Out) is collapsed into REFUSED today. I have reported what the code does and have not invented a state machine; if 03 defines the lifecycle, these rows should be re-read against it before any of them is estimated seriously.

**Conflicts and things the spec does not settle.**

1. Azure is required by three documents and deliberately blocked in code. 2. Spec 14's query-timeout-ms 120000 conflicts with the module's own governor argument, and nothing records a decision either way. AnalyticsLimits.java and the synthesis argue at length for tight bounds because DuckDB runs inside the ETL dispatcher's JVM behind a 4-permit ceiling; raising 30s to 120s quadruples how long one query can hold one of four permits. The design docs justify tight limits in general but never mention the spec's number, so this is an unreconciled conflict rather than a recorded deviation. The same applies to max-result-rows (10000 shipped vs 100000 specified).

3. Spec 12's operations axis presumes capability that does not exist. 1D/2D/3D analysis have no endpoint — /analytics.json exposes only schema, preview, profile and query (AnalyticsRestApi.java:85-187). 4. Spec 13's "guessed dataset IDs" security test has no premise. It presumes persisted datasets with IDs; analytics_dataset exists (V31, correct shape) but nothing in src/main/java writes it and it holds 0 rows on the live database.
