# Execution

Implement one groomed feature at a time. `Implement → Test → Fix → Review → Retest`, then the next.

Use [../prompts/execution.md](../prompts/execution.md) for the method. This file is the running order and the record of what has actually landed.

## Entry conditions for a feature

- [ ] `grooming/<feature>.md` exists, with numbered acceptance criteria
- [ ] `synthesis/<feature>.md` exists, with a gap table and an order
- [ ] Its open questions are answered, or explicitly deferred with the assumption written down
- [ ] Its dependencies are executed, or the work does not touch them

## Exit conditions

- [ ] Every acceptance criterion met, checked individually
- [ ] All four suites green (see below)
- [ ] Every new rule has a test that was **seen to fail** when the rule was removed
- [ ] Regression sections run for the affected areas — [../regression/regression.md](../regression/regression.md)
- [ ] QA pass recorded in `../qa/<feature>.md`
- [ ] Anything left undone stated plainly, with the reason

### Recorded against these conditions — `analytics-studio` phase one, 2026-09-08

The first module in this project to be built as **new work** rather than as a migration, and the
first to be recorded against the conditions above item by item. **Two exit conditions are not met
at all, two more only partly, and the entry conditions were met out of order.** They are listed as
such rather than argued away, because a checklist that only ever comes out green is a checklist
nobody is reading.

| Condition | Status on 2026-09-08 |
|---|---|
| Entry — `grooming/<feature>.md` with numbered acceptance criteria | **Not in the usual order.** The module was designed and built in a single session against a five-phase plan agreed with the user in that session; the `.ai/` documents for it were written alongside the build, not before it |
| Entry — `synthesis/<feature>.md` with a gap table and an order | Same. The phasing (phase one reads a file; SQL, profiling, charts, dashboards and benchmarks are phases two to five) **is** the order, and it was decided before the code — but it was decided in conversation first and written down second |
| Entry — open questions answered or deferred with the assumption written down | **Met, and one is still open on purpose:** Monaco is not in the project, so the SQL-editor choice is deferred to phase three rather than settled by default |
| Entry — dependencies executed, or untouched | **Met.** It depends on `storage-connections` (the connection record supplies the bucket) and on `object-browser`'s `storage.service.ts`, and changed neither |
| Exit — every acceptance criterion met, checked individually | **Met for the phase-one slice**, and only for that slice. Overview / Data (with the columns rail), folder-as-one-dataset, and the refusal paths were each exercised live against MinIO |
| Exit — all four suites green | **Partly.** Backend unit 607 and frontend 580 were run and are green. **E2E and the Kafka matrix were not run** |
| Exit — every new rule has a test that was **seen to fail** when the rule was removed | **Not met, and this is the one worth arguing about.** `DuckDbLockdownTest`'s seven tests were written *after* the lock-down they describe, so none of them has been observed failing against an unlocked session. | Exit — QA pass recorded in `../qa/analytics-studio.md` | **Not met. No QA pass has been done.** Live verification during the build is the author checking their own expectations, which is exactly what the QA phase exists not to be. There is no `qa/analytics-studio.md` |

15. `job-assistant`

QA pass: [../qa/reports.md](../qa/reports.md)
17. `workspace-requests`
18. `analytics-studio` — **added 2026-09-08**, and the only item here that is *new work* rather than a migration or a parity check, so "complete" has to be read against its own five-phase plan and not against the old app. **Phase one landed**: pick a storage connection, filter or walk to a file, read Overview / Data, or read a whole folder as one dataset. **Phases two to five have not been started** — no user-written SQL, no profiling, no charts, no dashboards, no saved queries, no benchmarks. Not persisted, not cached, not audited. **No QA pass**; see the condition-by-condition record above

**Taken out of order, and worth saying so.** `reports` is item 16 of what were then 17 and was worked on 2026-09-08 ahead of items 5-15, because the defects came in as live user QA on a screen already in front of the user rather than from this ordering. The consequence is visible in the row above: the *legibility* half of the feature is done and the *security* half — which the ordering would have reached first — is not.

**And `analytics-studio` was not in this order at all.** It could not have been: the order was derived
from the features that existed, and this module did not exist until the day it landed. It is recorded
here rather than treated as outside the process. What it did do is apply this document's own
principle *inside* one feature — the governor (`AnalyticsLimits`, the fair semaphore, the query
timeout) and the engine lock-down (`DuckDbSessionFactory`) were built **first**, before anything a
user can drive, precisely so that phase three's user-written SQL has somewhere safe to land. The
dangerous component here is the engine, not the caller, and the sequencing reflects that.
